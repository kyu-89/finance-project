## 0. Claude CLI 시작 지시문

이 문서는 단순 참고자료가 아니라 구현 기준서다. 개발 시 아래 원칙을 최우선으로 따른다.

1. 기존 Excel의 셀 위치를 그대로 복제하지 말고 **의미 기반 데이터 모델**로 재구성한다.
2. 기존 Excel에서 사용자가 직접 입력 가능한 항목은 웹에서도 빠짐없이 입력/수정 가능해야 한다.
3. Excel 수식은 셀 주소 기반이 아니라 데이터 의미에 기반한 계산 로직으로 구현한다.
4. 모든 금액 집계는 원천 데이터(raw record)를 기준으로 재계산 가능해야 한다. 집계값을 임의 저장하여 원천과 불일치시키지 않는다.
5. PC에서는 월 단위 대량입력/검토가 쉬워야 하고, 모바일에서는 10초 내 지출 1건 저장이 가능해야 한다.
6. Supabase의 모든 사용자 데이터 테이블은 RLS를 활성화하고 `auth.uid()` 기반으로 사용자별 데이터를 격리한다.
7. 클라이언트 코드에 `service_role` 키, DB 비밀번호, 개인 비밀키를 절대 포함하지 않는다.
8. Vercel 환경변수와 Supabase secret을 사용하고 `.env*`는 Git에 커밋하지 않는다.
9. 계좌번호 등 민감정보는 기본 마스킹한다.
10. 구현 도중 본 문서와 충돌하는 임의 UX/정책을 만들지 않는다. 불가피하면 TODO와 근거를 남긴다.
11. MVP라도 모바일/PC 반응형을 동시에 지원한다.
12. 계산 검증용 테스트를 반드시 작성한다. 특히 예산, 월 결산, 예적금, 대출, 자산 변동은 단위 테스트 대상이다.
13. 1차 메뉴는 `대시보드 / 월간관리 / 자산·금융 / 설정` **4개**를 기준으로 한다. 별도 `분석`, `예산·결산`, `장기관리`, `부채` 1차 메뉴를 다시 만들지 않는다.
14. 반복 금융거래는 매월 수기 입력시키지 않는다. 원천 상품/반복규칙에서 `planned`를 생성하고 사용자가 확인해 `posted`로 확정하는 흐름을 구현한다.

# 1. 제품 개요

## 1.1 제품 한 줄 정의

기존 Excel 가계부에 분산되어 있는 **수입·지출·예산·결산·카드·계좌·예적금·대출·보험·정부지원금·경조사·투자·자산** 정보를 하나의 개인 재무 데이터베이스로 통합하고, 모바일에서 빠르게 기록하며 PC에서 깊게 분석할 수 있는 개인 재무관리 웹 서비스.

## 1.2 핵심 문제

기존 Excel은 계산 기능은 충분하지만 다음 문제가 있다.

- 모바일에서 지출 즉시 입력하기 어렵다.
- 1~12월 시트가 분리되어 동일 로직이 반복된다.
- 행 추가/삭제, 범위 변경으로 SUMIF 범위나 셀 참조가 깨질 수 있다.
- 실제 파일에서 일부 `#REF!` 참조가 확인된다.
- 자산/계좌/예금/적금/대출/보험 데이터가 시트 단위로 분절되어 있다.
- 조회가 월별 시트 중심이라 연도·기간 비교와 드릴다운이 번거롭다.
- 카드/지출구분/대분류/소분류가 구조적으로 연결돼 있으나 Excel에서는 데이터 검증과 수식에 의존한다.
- 금융정보가 한 파일에 있으므로 파일 유출 시 위험이 크다.

## 1.3 제품 목표

### G1. 입력 마찰 최소화
모바일에서 결제 직후 **금액 → 카테고리 → 결제수단** 중심으로 10초 내 저장 가능.

### G2. Excel 기능 완전 대체
기존 사용자가 입력하던 모든 필드와 핵심 계산식을 지원.

### G3. 통합 재무 현황 파악
대시보드에서 `연도 → 월 → 일 → 거래` 및 `대분류 → 소분류 → 거래`로 드릴다운.

### G4. 자산의 흐름까지 관리
가계부 손익뿐 아니라 금융자산·부동산·부채를 포함한 순자산 추이를 월별로 추적.

### G5. 무료 범위 내 높은 보안
Supabase Free + Vercel 기반으로 운영하며 SMS 비용이 필요한 인증은 MVP에서 제외. 이메일 인증 + TOTP MFA를 사용.


### G6. 재무 숫자의 의미 일관성
현금 유출입, 소비, 저축·투자, 부채상환, 자산형성을 서로 다른 개념으로 분리하여 어떤 화면에서도 동일한 정의와 집계식을 사용한다.

## 1.4 핵심 재무 분류 체계

이 서비스는 모든 돈의 흐름을 다음 관점으로 구분한다.

1. **현금유입(Cash Inflow)** — 계좌/현금으로 실제 들어온 돈
2. **현금유출(Cash Outflow)** — 계좌/현금에서 실제 나간 돈
3. **소비(Consumption)** — 생활을 위해 소진된 비용
4. **저축·투자(Saving & Investment)** — 현금이 다른 자산으로 이동한 금액
5. **부채원금상환(Debt Principal Repayment)** — 현금이 나가면서 부채가 감소한 금액
6. **금융비용(Finance Cost)** — 대출이자/수수료처럼 실제 비용으로 소진된 금액
7. **자산형성(Wealth Building)** — 저축 + 투자 + 부채원금상환
8. **순자산(Net Worth)** — 총자산 - 총부채

핵심 원칙:

> 현금이 나갔다고 모두 비용이 아니다.

예:
- 적금 50만원 → 현금유출이지만 소비 아님, 자산형성
- 주식 매수 30만원 → 현금유출이지만 소비 아님, 자산형성
- 대출원금 90만원 → 현금유출이지만 소비 아님, 부채감소이자 자산형성
- 대출이자 30만원 → 현금유출이면서 금융비용
- 식비 20만원 → 현금유출이면서 소비

### 핵심 집계식

```text
생활수지 = 총수입 - 소비성지출 - 금융비용

자산형성액 = 저축 + 투자순유입 + 대출원금상환

현금잔여액 = 총현금유입 - 총현금유출

순자산 = 총자산 - 총부채

순자산증가액 = 현재 순자산 - 비교시점 순자산
```

`자산형성률` 기본 정의:

```text
자산형성률 = 자산형성액 ÷ 총수입
```

단, 자산가격 상승/하락에 따른 평가손익은 자산형성액에 포함하지 않고 순자산 변동의 별도 요인으로 구분한다.

# 3. 핵심 데이터 모델

## 3.1 모델링 원칙

Excel의 “월별 시트”는 DB에 만들지 않는다. 모든 거래는 단일 `transactions` 테이블에 저장하고 `transaction_date`로 월/연도를 구분한다.

핵심 관계:

```text
user
 ├─ households
 │   ├─ members
 │   ├─ categories
 │   ├─ payment_methods
 │   ├─ transactions
│   ├─ transaction_support_details
│   ├─ transaction_event_details
 │   ├─ recurring_rules / recurring_occurrences
 │   ├─ budgets
 │   ├─ accounts
 │   ├─ deposits
 │   ├─ savings
 │   ├─ loans
 │   ├─ insurances
 │   ├─ assets
│   ├─ financial_goals / financial_tasks
 │   └─ monthly_asset_snapshots
```

개인 1인 사용이라도 `household_id`와 `household_members`를 둔다. 본인/배우자/자녀 등 가족 구성원 명의의 거래·계좌·자산·부채·보험을 하나의 가구 안에서 관리할 수 있어야 한다.

가족 구성원은 단순 라벨이 아니라 모든 재무 데이터의 공통 분석 축이다.
- 기본 구성원 예시: 본인, 배우자, 자녀1, 자녀2
- 사용자가 자유롭게 추가/수정/비활성화 가능
- 각 구성원은 `member_type`(`self`, `spouse`, `child`, `other`)과 표시명 보유
- 거래, 계좌, 카드, 예금, 적금, 대출, 보험, 기타자산 등에 `owner_member_id` 또는 관계 필드를 둔다.
- 공동명의/공동사용은 `ownership_type=joint` 및 필요 시 복수 구성원 연결 테이블로 표현한다.
- 대시보드의 기본 조회 범위는 `가구 전체`이며 구성원별 필터로 즉시 전환 가능해야 한다.
- 자녀가 성장하여 별도 로그인 계정을 갖게 되더라도 과거 명의 데이터가 끊어지지 않도록 `household_member`와 `auth.users`는 분리하고 선택적으로 연결한다.
- Excel에서도 명의자/피보험자/비고 등에 가족 구성원이 반복 등장하므로 초기 Import 시 구성원 매핑 단계를 제공한다.

## 3.2 공통 컬럼

모든 주요 테이블:

- `id uuid primary key default gen_random_uuid()`
- `user_id uuid not null references auth.users(id)` 또는 `household_id`
- `created_at timestamptz default now()`
- `updated_at timestamptz default now()`
- 필요한 경우 `deleted_at timestamptz null` (soft delete)

금액은 부동소수점 사용 금지.
- 원화: `bigint`
- 금리/비율: `numeric(10,6)`

# 4. 거래 원장 기능 정의

## 4.1 거래 종류

`transaction_type`
- `income` 수입
- `expense` 소비성 지출
- `saving` 저축/예적금 납입
- `investment` 투자자산 매수/투입
- `debt_principal` 대출 원금 상환
- `finance_cost` 대출 이자/금융 수수료
- `transfer` 계좌 간 이동
- `asset_adjustment` 평가액/자산 조정
- `refund` 환불/취소

Excel의 수입과 소비성/저축성 지출을 모두 표현해야 한다.

### 비용 성격(cost behavior)

소비성 비용(`expense`)과 금융비용(`finance_cost`)은 카테고리와 별개로 **고정비 / 변동비** 분석축을 가질 수 있다.

`cost_behavior`
- `fixed` — 고정비
- `variable` — 변동비
- `null` — 수입/저축/투자/대출원금/이체/자산조정 등 비용 성격을 적용하지 않는 거래

고정비/변동비는 대분류를 대체하지 않는다. 예를 들어 `주거 > 월세`는 카테고리이고 `fixed`는 비용 성격이다.

기본 원칙:
- 고정비: 정기적으로 발생하고 단기간에 조정하기 어려운 생활 유지성 비용
- 변동비: 사용량/선택/소비행동에 따라 금액 또는 발생 여부가 달라지는 비용
- 반복거래라고 해서 반드시 고정비는 아니다.
- 사용자가 거래별로 예외 수정할 수 있어야 한다.
- 카테고리에 `default_cost_behavior`를 설정하여 신규 거래 입력 시 자동 제안한다.
- 반복규칙에도 `cost_behavior`를 저장하여 자동생성 planned 거래에 승계한다.

기본 예시:
- 월세/정액 관리비/보험료/통신 기본요금/정기 구독 → fixed
- 식비/외식/쇼핑/여가/교통 사용액/여행 → variable
- 전기·가스·수도처럼 매월 발생하지만 사용량에 따라 달라지는 비용 → variable
- 적금 납입/대출 원금상환 → 비용이 아니라 저축/부채감소이므로 fixed/variable 비용 집계에서 제외
- 대출 이자는 금액이 매월 달라져도 단기간에 회피하기 어려운 의무성 비용이므로 기본값 `fixed`를 제안할 수 있다.
- 고정비/변동비는 금액이 매월 동일한지 여부가 아니라 **비용의 경제적 성격과 단기간 조정 가능성**으로 판단한다.

## 5.3 PC 월간관리 — 해당 월의 메인 작업공간

`월간관리`는 사용자가 한 달을 정리할 때 가장 자주 여는 핵심 메뉴다. 단순 거래 입력표가 아니라 **해당 월에 사용자가 입력·확인해야 하는 모든 월간성 재무 데이터를 한 곳에서 처리**할 수 있어야 한다.

상단 월 선택: `2026년 8월 ◀ ▶`

내부 탭:
1. **월간입력** — 수입/지출/저축/상환/이체/반복예정 항목 입력·확인
2. **전체내역** — 해당 월의 모든 거래 원장 조회·수정
3. **예산·결산** — 월 예산 편집, 실제 대비, 결산 메모
4. **반복항목** — 보험료·예적금·대출·구독·급여 등 이번 달 자동 생성 예정항목 확인
5. **월말점검** — 계좌잔액, 자산평가액, 대출잔액 등 월말 스냅샷 입력·확정

`월간입력` 스프레드시트 컬럼:
- 날짜
- 상태(예정/확인/실적)
- 유형
- 결제수단/출금계좌
- 대분류
- 소분류
- 내용
- 금액
- 관련 상품/계약
- 명의자/사용자/비용대상
- 비고

정책:
- 행 추가 단축키
- 이전 행 값 복사
- 셀 단위 키보드 이동
- 드롭다운 검색
- 여러 행 붙여넣기
- 저장 전 변경 행 표시
- 월 총 수입/소비/저축/상환/차액 즉시 갱신
- 모바일에서 기록한 거래도 즉시 같은 월에 표시
- 반복 규칙에서 자동 생성된 `planned` 항목도 같은 표에 표시하되 시각적으로 구분
- 사용자가 금액/일자를 수정한 뒤 `확인`하면 실거래 `posted`로 전환
- 이미 모바일에서 동일 건을 직접 입력했다면 중복 후보를 감지하여 자동 생성 예정건과 매칭
- CSV/XLSX Import를 위한 매핑 UI는 Phase 1.5

**중요:** 월간관리에서 상품의 원천 계약정보(보험 가입일, 적금 이율, 대출 만기 등)를 매월 다시 입력하지 않는다. 그런 정보는 `자산·금융`의 상품 상세가 source of truth이며, 월간관리에는 그 달에 발생하는 납입/상환/평가/잔액만 노출한다.

## 5.4 거래 수정/삭제

- 수정 시 모든 대시보드/예산/자산연계 집계 즉시 반영
- 삭제는 soft delete 권장
- 최근 삭제 기록 30일 복구 가능
- 대량 삭제는 확인 모달
- 반복항목에서 생성된 실거래를 삭제해도 원천 반복규칙 자체는 삭제하지 않는다. 해당 월만 `skip` 처리할지, 이후 반복도 중지할지 명확히 선택시킨다.

## 5.5 반복항목 자동 생성 엔진 — 핵심 정책

보험료, 적금 납입, 예금 월이자/정기 납입형 상품, 대출 상환, 월세, 통신비, 구독료, 급여 등 **정기적으로 발생하는 금액은 매월 수기 재입력하지 않는다.**

### 5.5.1 Source of truth

반복항목은 두 종류로 생성된다.

1. **상품/계약 연동형**
   - 보험 → 월 보험료
   - 적금 → 월 적립액
   - 대출 → 예정 원금/이자/상환금
   - 필요 시 예금/연금/기타 금융상품
2. **일반 반복거래형**
   - 월세
   - 통신비
   - 구독료
   - 용돈
   - 급여
   - 기타 고정 수입/지출

상품 연동형에서는 상품 마스터가 원천이다. 동일 정보를 `recurring rule`에 중복 저장하지 말고 필요한 필드만 참조하거나 버전 이력을 관리한다.

### 5.5.2 반복 규칙 필드

- source_type: insurance / saving / loan / subscription / salary / manual 등
- source_id nullable
- 시작일
- 종료일 nullable
- 반복주기: monthly / weekly / yearly / custom
- 월 납부일 또는 반복 규칙
- 기본금액
- 거래유형
- 카테고리/소분류
- 결제수단/출금계좌
- 명의자/사용자/비용대상
- 상태: active / paused / ended
- 자동생성 여부

### 5.5.3 월 자동 생성

- 활성 규칙은 해당 월 진입 또는 서버 배치 시 그 달의 `planned transaction`을 idempotent하게 1건 생성한다.
- 동일 `recurring_rule_id + occurrence_date` 조합은 1건만 존재해야 한다.
- 생성된 예정건은 **월간입력에 자동으로 채워진다.**
- 사용자는 예정건을 확인하고 실제 금액/일자/결제수단을 수정한 뒤 `posted`로 확정한다.
- 반복항목의 기본 상태는 `planned`. 실제 금융기관 연동이 없는 MVP에서 자동으로 `posted` 처리하지 않는다.

### 5.5.4 변경·해지·일시중지

금액 또는 조건 변경 시 다음 중 하나를 선택:
- 이번 달만 변경
- 이번 달부터 이후 모두 변경

해지/종료 시:
- 종료일 이후 예정건 생성 금지
- 이미 생성된 미래 planned 건은 취소
- 과거 posted 거래는 보존

일시중지 시:
- pause 기간 동안 생성하지 않거나 생성건을 skipped 처리
- 재개 시 이후 회차부터 정상 생성

### 5.5.5 미납/건너뛰기

이번 달 실제 납입이 없으면:
- `skip` 처리 가능
- 실적 집계에는 미반영
- 예정/미납 현황에는 남김
- 적금/대출처럼 상품 잔액과 연결되는 경우 자동으로 잔액을 감소/증가시키지 않음

### 5.5.6 중복방지

모바일에서 사용자가 보험료를 먼저 직접 입력한 뒤 월간관리에서 반복예정건을 확인하는 상황을 지원한다.

중복 후보 기준 예시:
- 동일/유사 금액
- 같은 월 또는 납부예정일 ±3일
- 동일 결제수단
- 동일 카테고리 또는 source product

후보 발견 시 `기존 거래와 연결`을 제안하며, 연결 후 planned 건은 posted 거래를 가리키도록 한다. 절대 두 건을 모두 실적 합산하지 않는다.

## 5.6 자산·금융 상품과 월간관리 연계

### 보험
보험 상품에서 `월보험료`, 납부일, 시작일, 종료/해지일, 결제수단을 등록하면 해지/종료 전까지 월간입력에 예정 보험료가 자동 생성된다.

### 적금
적금에서 `월 적립액`, 납부일, 가입일, 만기일, 출금계좌를 등록하면 만기/해지 전까지 매월 planned 납입거래가 생성된다. posted 확정 시 해당 적금의 납입 누계/현재저축액 계산에 연결한다.

### 예금
거치식 예금처럼 월 납입이 없는 상품은 반복지출을 생성하지 않는다. 월 이자 지급형 등 실제 반복 현금흐름이 있는 경우에만 수입 예정건을 생성한다.

### 대출
상환스케줄이 있는 대출은 월별 예정 상환건을 생성한다. 거래에는 원금/이자를 구조적으로 분리하여 소비지출과 부채감소를 이중 계산하지 않는다.

### 보험·적금·대출 공통
- 원천 상품이 해지/만기/상환완료되면 이후 자동생성 즉시 중단
- 상품 금액 변경은 효력시작일 기반 버전으로 관리
- 과거 거래는 당시 금액을 보존
- 월간 입력에서 수정한 1회성 실제금액이 원천 상품의 기본금액을 자동 변경하지 않음

# 6. Excel 계산 로직 → 웹 계산 정책

## 6.1 월 총계

- 월 총수입 = 해당 월 **`posted` 상태** `income` 합계
- 월 저축성지출 = 해당 월 **`posted` 상태** `saving` 합계
- 월 소비성지출 = 해당 월 **`posted` 상태** `expense` 합계
- 월 총지출 = 저축성지출 + 소비성지출
- 월 차액 = 총수입 - 총지출
- 순소비 기준 가처분 잔액은 별도 지표로 제공 가능

Excel처럼 고정수입/부가수입을 입력 위치로 구분하지 않고 `income_group=fixed|additional`로 구분한다.

## 6.2 예산 잔액

Excel의 순차 수식 `이전 잔액 - 현재 지출`을 의미 기반으로 변경.

`예산 잔액 = 해당 월/예산범위 예산 - 해당 범위 누적 실지출`

- 날짜나 행 순서가 변경돼도 값이 깨지지 않아야 한다.
- 소비성 지출 예산이 기본.
- 필요 시 저축 목표는 별도 목표로 관리.

## 6.3 연간 항목별 수입

Excel `SUMIF(월시트 소분류, 기준항목, 금액)`을 DB GROUP BY로 치환.

그룹핑 가능:
- 년 → 월 → 소분류 → 거래
- 소분류 → 년 → 월 → 거래

## 6.4 연간 카드별 지출

`SUM(expense/saving.amount) GROUP BY payment_method, month`

카드/계좌별:
- 월 사용액
- 연 사용액
- 평균 월 사용액
- 전월 대비
- 전년동월 대비
- 전체 지출 점유율

## 6.5 연간 대분류/소분류 지출

- 대분류 합계 = 하위 소분류 `posted` 실지출 합계
- 소분류 합계 = 해당 소분류 거래 합계
- 연 평균 = 연 합계 / 조회 월수
- 구성비 = 해당 항목 합계 / 전체 지출 합계

Excel처럼 고정 12개월만 나누지 말고 조회 범위가 YTD라면 실제 포함 개월 수를 기본으로 한다. 단, `연 환산 평균` 옵션은 별도 제공 가능.

## 6.6 월 결산

기존 Excel 결산의 핵심 의미를 다음처럼 정의한다.

- 수입 예산차 = 실제 수입 - 계획 수입
- 저축성지출 예산차 = 실제 저축 - 저축 예산
- 소비 대분류별 예산잔액 = 예산 - 실제 지출
- 총 예산 대비 실제 지출률 = 실제 / 예산
- 저축률 = 저축성지출 / 총수입
- 소비율 = 소비성지출 / 총수입

저축률 목표는 설정 테이블에서 연/월별 지정 가능.

## 6.7 예금 계산

Excel 기준:
- 가입기간(개월) = 가입일~만기일 개월수
- 남은기간 = max(0, 오늘~만기일 개월수)
- 기간 분류: 장기/중기/단기
- 세전이자 = 원금 × 연이율 × (가입개월/12)
- 세후이자 = 세전이자 × (1 - 세율)
- 예상수령액 = 원금 + 세후이자

기간 분류는 기존 Excel 정책을 그대로 초기 적용:
- 37개월 초과: 장기
- 36개월 미만: 단기
- 그 외: 중기

※ 36/37개월 경계가 다소 비직관적이므로 UI 설정에서 향후 조정 가능하게 한다.

## 6.8 적금 계산

필드:
- 월 적립액
- 이율
- 과세율
- 방식: 단리 / 월복리
- 가입개월

계산:
- 만기 원금 = 월 적립액 × 가입개월
- 단리 세전이자 = 월 적립액 × [가입개월×(가입개월+1)/2] × (연이율/12)
- 월복리 세전이자 = 월복리 미래가치 - 납입원금
- 세후이자 = 세전이자 × (1-과세율)
- 예상수령액 = 만기 원금 + 세후이자

Excel의 `FV()` 동작과 동일 결과가 나오는 테스트 케이스를 만든다.

## 6.9 대출 계산

대출 기본정보:
- 기관명
- 대출명
- 대출금액
- 연이자율
- 상환방법
- 대출일
- 만기일
- 거치기간(개월)

상환내역:
- 회차
- 상환일
- 납입원금
- 대출이자
- 월상환금
- 누적상환금
- 대출잔금
- 비고

계산:
- 월상환금 = 납입원금 + 대출이자
- 누적상환금 = 이전 누적 + 월상환금
- 대출잔금 = 이전 잔금 - 납입원금
- 총 대출이자 = 모든 상환내역 이자 합
- 총 상환금액 = 모든 월상환금 합
- 현재누적상환금 = 오늘 이전 가장 최근 상환건의 누적상환금
- 현재대출잔금 = 오늘 이전 가장 최근 상환건의 대출잔금
- 남은기간 = max(0, 오늘~만기일 개월수)

Excel의 `VLOOKUP(TODAY(), 상환표...)` 의미는 “오늘 이하 가장 최근 상환 스냅샷” 조회로 구현한다.

## 6.10 순자산

- 금융자산 = 계좌 + 예금 현재가치/원금 + 적금 현재저축액 + 투자계정 등
- 부동자산 = 사용자가 등록한 기타자산 현재평가액
- 총자산 = 금융자산 + 비금융자산
- 총부채 = 현재 대출잔금 합계
- 순자산 = 총자산 - 총부채
- 부채비율 = 총부채 / 순자산 (0 또는 음수 예외처리)

월말 또는 사용자가 `스냅샷 저장` 시 `monthly_asset_snapshots`에 기록한다.

## 6.11 자산 변동

- 월 증감액 = 현재월 순자산 - 전월 순자산
- 월 증감률 = 증감액 / 전월 순자산

기존 Excel은 일부 증감률이 `변동액 / 현재월 자산`으로 되어 있으나, 웹 대시보드의 일반적인 비교 지표는 **전월 값 대비 증감률**로 정의한다. Excel과 완전히 동일한 수치가 필요한 경우 `legacy_change_rate`를 별도 표시하거나 설정 가능하게 한다.

첫 화면에서 “이번 달 재무상태가 좋은지 나쁜지”를 5초 내 판단하고, 궁금한 숫자를 클릭하면 원인 거래까지 내려갈 수 있어야 한다.

- 최근 3개월
- 최근 6개월
- 최근 12개월
- 사용자 지정

비교:
- 이전 기간 대비
- 전년 동기 대비
- 전년 동일 월 대비
- 비교 없음

예: `2026-01-01 ~ 2026-08-27` 조회 시 전년동기는 `2025-01-01 ~ 2025-08-27`.

9. 순자산
10. 순자산 증감

각 KPI는 비교기간의 값, 증감액, 증감률을 함께 표시.

## 8.4 드릴다운 구조

### 시간 기준
`연도 → 월 → 일 → 거래`

`전체 → 카드/현금/계좌 → 대분류 → 소분류 → 거래`

## 8.5 필수 시각화

# 12. 정부지원금 — 거래 통합 + 기간 기반 예정건 자동생성

정부지원금은 별도 1차/2차 메뉴를 만들지 않는다. **실제 돈의 유입은 `transactions`의 수입 거래가 source of truth**다.

다만 정부지원금은 여러 달에 걸쳐 반복 수령되는 경우가 많으므로, 사용자가 전체 수령기간과 지급주기를 한 번 입력하면 월별 예정 수입을 자동 생성해야 한다.

## 12.1 지원금 마스터/상세정보

기존 Excel의 정부지원금 시트 정보를 보존하기 위해 `transaction_support_details`를 사용한다.

주요 필드:
- 지원금 종류
- 대상/구간
- 세부 대상 연령/조건
- 신청기간 시작/종료
- 전체 수령기간 시작/종료
- 지급주기: monthly / quarterly / yearly / one_time / custom
- 지급 기준일 또는 예상 입금일
- 회차별 예상금액
- 총 예상 지원금
- 상태
- 접수처
- URL
- 메모
- 실제 수령 대상 가족구성원
- 실제 입금 계좌

상태 enum:
- planned
- eligible
- applied
- approved
- receiving
- completed
- rejected
- expired

## 12.2 예정 수입 자동생성

지원금이 승인되었거나 사용자가 수령 예정으로 등록한 경우:

```text
전체 수령기간 + 지급주기 + 회차별 예상금액
        ↓
지원금 반복규칙 생성
        ↓
해당 월별 planned 수입 거래 자동 생성
        ↓
월간관리 > 월간입력에 표시
        ↓
실제 입금 확인
        ↓
posted 확정
```

예시:

```text
부모급여
수령기간: 2026-01 ~ 2026-12
지급주기: 매월
예상 입금일: 매월 25일
회차별 예상금액: 1,000,000원
```

→ 2026년 1월부터 12월까지 매월 25일에 `planned / income / 정부지원금` 거래 12건을 자동 생성한다.

지원금 예정건도 일반 반복거래 엔진을 재사용한다. 별도 스케줄러를 만들지 않는다.

## 12.3 실제 입금 처리

실제 입금되면 해당 회차의 planned 거래를 posted로 전환한다.

- 실제 입금일 수정 가능
- 실제 입금액 수정 가능
- 차액이 있어도 과거 예정금액을 덮어쓰지 않고 occurrence 기준으로 실제값을 기록
- 입금되지 않은 회차는 planned 또는 미수령 상태 유지
- 실제 거래가 먼저 입력된 경우 예정건과 매칭하여 중복 방지

## 12.4 기간/금액 변경

지원금 정책 변경 또는 수급조건 변경을 지원한다.

- 수령기간 단축 → 이후 planned 자동생성 중단
- 수령기간 연장 → 추가 planned 자동생성
- 회차별 금액 변경 → effective date 이후 금액 변경
- 이번 회차만 금액 변경 → 해당 occurrence만 수정
- 지급일 변경 → 적용월 이후 예정일 변경
- 일시중지 → 지정 기간 예정건 생성 중단
- 조기 종료 → 이후 occurrence cancelled 처리

## 12.5 UX

등록 진입점:
- `월간관리 > 반복항목 > 지원금 예정 등록`
- 또는 `월간관리 > 전체내역 > 수입 추가 > 정부지원금 > 반복 수령 설정`

입력 UX:
1. 지원금명
2. 대상 구성원
3. 전체 수령기간
4. 지급주기
5. 예상 입금일
6. 회차별 예상금액
7. 입금계좌
8. 선택 상세정보(신청기간/조건/접수처 등)

저장 후 사용자에게 `총 예정 회차 / 총 예상금액 / 첫 예정일 / 마지막 예정일`을 미리 계산해 보여준다.

## 12.6 조회/분석

- `월간관리 > 전체내역`에서 카테고리 `정부지원금` 필터
- 상태 `planned / posted` 구분
- 대시보드에서 `예정 지원금 / 실제 수령액 / 미수령 예정액` 확인
- 연도 → 월 → 지원금 종류 → 실제 거래 드릴다운
- 가족구성원 기준 조회 지원

집계 규칙:
- 실제 수입 KPI에는 `posted`만 포함
- planned는 별도 `예정수입` 지표로만 표시
- 총 예상 지원금은 반복규칙/occurrence에서 계산
- 실제 수령 누계는 posted 거래 합계
- 미수령 예정액 = 아직 posted 되지 않은 planned occurrence의 예상금액 합계

# 13. 경조사 — 거래 통합 정책

경조사 역시 별도 메뉴/별도 금액 원장을 만들지 않는다. **금액의 source of truth는 `transactions`**다.

- 내가 냄 → `expense`
- 내가 받음 → `income`
- 기본 카테고리 → `경조사`

기존 Excel의 사람/관계/행사 정보를 보존하기 위해 `transaction_event_details`를 거래의 1:0..1 확장 테이블로 둔다.

확장 필드:
- 이벤트 유형: 축의/부의/기타
- 상대방 이름
- 관계/그룹
- 행사 설명
- 관련 가족구성원
- 메모

UX:
- `월간관리 > 전체내역`에서 경조사 카테고리 거래 입력/조회
- 거래 상세 Drawer에서 `경조사 상세` 확장영역 제공
- 모바일 빠른 입력에서는 기본 거래만 빠르게 저장하고 `상세 추가`를 통해 상대방/관계 등을 선택 입력
- 별도 경조사 메뉴는 만들지 않는다.

분석:
- 대시보드 또는 전체내역 필터에서 `경조사` 선택
- 인물별 주고받은 누계
- 행사유형별
- 연도별
- 최근 교류

위 분석은 `transactions` + `transaction_event_details` JOIN으로 계산하며 별도 금액 집계 테이블을 만들지 않는다.

# 14. 투자 관리

업비트 시트의 기존 필드:
- 거래일자
- 코인
- 종류(매수/매도)
- 거래단가
- 거래금액
- 수수료
- 정산금액
- 비고

계산:
- 매수 수수료 = 거래금액 × 수수료율
- 매수 정산 = 거래금액 + 수수료
- 매도 수수료 = 거래금액 × 수수료율
- 매도 정산 = 거래금액 - 수수료
- 코인별 총매수 = 매수 정산 합
- 코인별 총매도 = 매도 정산 합
- 단순 실현 손익(기존 Excel 방식) = 총매도 - 총매수

주의: 이는 세법상/회계상 정확한 원가배분 손익과 다를 수 있으므로 UI에 `단순 누적 손익`으로 명시한다. 향후 평균매입가/FIFO 지원 가능.

# 16. 인증/보안 정책

## 16.1 결론

### 휴대폰 SMS OTP
MVP에서 사용하지 않는다.

이유:
- Supabase Phone Login은 Twilio, MessageBird, Vonage 등 SMS provider 설정이 필요하다.
- SMS 발송 비용이 발생할 수 있어 “유료면 안 함” 조건과 충돌한다.
- Supabase의 고급 Phone MFA 자체도 무료 플랜 대상이 아니다.

### 권장 인증
**Email + Password(또는 Magic Link) + TOTP MFA 강제**

Supabase TOTP MFA는 무료이며 Authenticator 앱을 사용한다.

권장 온보딩:
1. 이메일 가입
2. 이메일 확인
3. 최초 로그인 직후 TOTP 등록 강제
4. QR을 Google Authenticator / 1Password / Apple Passwords 등에 등록
5. 코드 검증 성공 시 AAL2 세션
6. 이후 핵심 화면은 AAL2 요구

## 16.2 Supabase 보안

### RLS 필수
모든 개인 데이터 테이블:

```sql
alter table public.transactions enable row level security;
```

정책 기본 형태:

```sql
create policy "users can select own data"
on public.transactions
for select
to authenticated
using ((select auth.uid()) = user_id);
```

INSERT/UPDATE/DELETE를 별도 policy로 작성한다.

### 권한 최소화
- `anon`: 개인 데이터 테이블 권한 없음
- `authenticated`: 필요한 CRUD만
- `service_role`: 브라우저 접근 절대 금지

### MFA 강제
RLS 또는 서버 레이어에서 JWT `aal = aal2`를 요구하는 정책 검토.
특히 다음 화면:
- 계좌 전체번호 보기
- 데이터 내보내기
- 전체 데이터 삭제
- MFA 설정 변경

## categories 추가 정책

`categories` 및 필요 시 `subcategories`에 다음 기본값을 둔다.

```sql
default_cost_behavior text null -- fixed|variable
```

거래 생성 시 카테고리 기본값을 `transactions.cost_behavior`에 복사한다. 이후 카테고리 기본값이 변경되어도 과거 posted 거래의 비용 성격을 일괄 변경하지 않는다.

`recurring_rules`에도 다음 필드를 둔다.

```sql
cost_behavior text null -- fixed|variable
```

반복규칙에서 생성된 occurrence/transaction은 이 값을 승계한다.

# 19. 정보구조(IA)

## 19.1 IA 최종 설계 원칙

사용자 입장에서 1차 메뉴는 **4개**만 사용한다.

1. **대시보드** — 현황 파악/분석/드릴다운 + 목표/예정일 확인
2. **월간관리** — 이번 달 입력·전체거래·예산·결산·반복항목·월말점검
3. **자산·금융** — 계좌/카드/예적금/투자/대출/보험/기타자산
4. **설정** — 가족/분류/목표·일정/데이터/보안

별도의 `분석`, `예산·결산`, `장기관리`, `부채`, `지원금`, `경조사` 1차/2차 메뉴를 만들지 않는다.

정부지원금과 경조사는 실제 현금흐름이므로 월간 거래에 통합한다. 목표·일정은 거래가 아니므로 설정에서 관리하고 대시보드에서 확인한다.

## 19.2 공통 글로벌 영역

PC 상단 헤더 또는 모바일 상단:
1. 가구/구성원 전환기 — 가구 전체 / 본인 / 배우자 / 자녀…
2. 조회기간 — 화면 성격에 맞게 월/연/사용자지정
3. 알림/예정 일정
4. 사용자 메뉴

가구/구성원 선택은 현재 화면을 유지하면서 데이터만 필터링한다.

## 19.3 PC 웹 최종 메뉴 구조

```text
[상단] 우리집 ▼ | 가구 전체 ▼ | 2026년 8월 ▼        알림  프로필

1. 대시보드

2. 월간관리
   ├─ 월간입력
   ├─ 전체내역
   ├─ 예산·결산
   ├─ 반복항목
   └─ 월말점검

3. 자산·금융
   ├─ 전체
   ├─ 계좌·카드
   ├─ 예·적금
   ├─ 투자
   ├─ 대출
   ├─ 보험
   └─ 기타자산

4. 설정
   ├─ 가족 구성원
   ├─ 카테고리·결제수단
   ├─ 목표·일정
   ├─ 데이터 가져오기/내보내기
   └─ 보안·계정

                                      [ + 거래 기록 ]
```

통합 이유:
- 홈 + 분석 → 대시보드
- 가계부 + 예산·결산 → 월간관리
- 자산 + 부채 + 보험 → 자산·금융
- 지원금 + 경조사 → 월간 거래에 통합
- 목표·일정 → 설정에서 마스터 관리, 대시보드에서 확인

## 19.4 PC 핵심 화면

### ① 대시보드
- 이번 달 수입/소비/저축/현금흐름
- 예산소진율
- 총자산/총부채/순자산
- 전월/전년동월/전년동기 비교
- 월별 현금흐름·순자산 추이
- 카테고리/결제수단/구성원 분석
- 목표 진행률
- 지원금 신청기한, 보험갱신 등 예정 일정
- 모든 재무 KPI/그래프에서 실제 거래까지 드릴다운

### ② 월간관리 > 월간입력
- 해당 월의 모든 월간성 입력/확인 업무
- 직접입력 + 모바일입력 + 반복 예정거래 통합
- 지원금 수령/경조사 수입·지출도 일반 거래와 동일한 원장에 기록
- 예산/결산/월말점검은 같은 메뉴 내 탭 전환

### ③ 자산·금융
- 상품 마스터와 현재 재무상태 관리
- 보험/적금/대출 등에 반복조건 등록 → 월간관리 자동 반영
- 상품 자체를 매월 재입력하지 않음

## 19.5 모바일 웹/PWA 최종 구조

```text
┌──────────────────────────┐
│ 우리집   가구 전체 ▼          │
│ 2026년 8월                  │
├──────────────────────────┤
│          현재 화면            │
├──────────────────────────┤
│ 홈   내역    ＋    자산   더보기 │
└──────────────────────────┘
```

- **홈**: 대시보드 요약 + 목표/임박일정
- **내역**: 전체 거래 타임라인, planned 필터
- **＋ 기록**: 금액 → 분류 → 결제수단 → 저장. 정부지원금/경조사도 카테고리 선택 후 필요 시 상세정보 추가
- **자산**: 순자산 + 계좌·카드/예·적금/투자/대출/보험
- **더보기**: 월간관리(예산·결산/반복항목/월말점검), 지원금 예정 등록, 목표·일정 관리, 가족, 카테고리·결제수단, 데이터, 보안·계정

## 19.6 비용 성격 UX

고정비/변동비는 사용자가 매 거래마다 고민하게 만들지 않는다.

- 빠른 입력: 카테고리 선택 시 자동 지정, 기본 화면에서는 숨김
- 상세 입력: 필요 시 변경
- 월간입력: 비용성격 컬럼 조회/필터/일괄수정
- 전체내역: 고정비/변동비 필터
- 대시보드: 전체 소비 → 고정비/변동비 → 카테고리 → 거래 순으로 드릴다운
- 반복항목: 규칙에 비용성격을 지정하고 생성 거래에 자동 승계
- 고정비라고 해서 자동으로 반복항목으로 만들지는 않는다. `고정/변동`과 `반복 여부`는 서로 독립된 속성이다.

## 19.7 가족/명의 데이터 UX

가계부에서 `결제한 사람`, `명의자`, `실제 비용 대상`이 다를 수 있으므로 하나의 사람 필드로 축약하지 않는다.

- **명의자(owner):** 계좌·카드·예금·보험·자산의 법적/관리상 명의
- **거래자(payer/user):** 실제 결제 또는 자금 이동을 발생시킨 구성원
- **비용대상(beneficiary):** 실제 누구를 위한 소비인지

예시:
- 본인 카드로 자녀 학원비 → 카드 명의자 본인 / 거래자 본인 / 비용대상 자녀1
- 자녀 명의 적금에 본인이 납입 → 상품 명의자 자녀1 / 자금원 본인

대시보드에서 `명의 기준`, `거래자 기준`, `비용대상 기준` 분석을 지원한다.

## 19.8 핵심 사용자 여정

### A. 오늘 커피를 샀다
`모바일 + → 금액 → 카테고리 → 카드 → 저장`

### B. 월 보험료/적금은 자동으로 들어온다
`자산·금융에서 상품 1회 등록 → 반복규칙 활성 → 매월 월간관리 planned 자동 생성 → 실제 납부 확인`

### C. 이번 달 가계부를 정리한다
`PC → 월간관리 → 월간입력 → 모바일/자동생성 건 확인 → 누락 추가 → 예산·결산 → 월말점검`

### D. 왜 이번 달 지출이 늘었는지 본다
`대시보드 → 전월 대비 +18% → 식비 +31% → 외식 → 실제 거래목록`

### E. 우리 집 자산이 작년보다 얼마나 늘었는지 본다
`대시보드 또는 자산·금융 > 전체 → 전년동월 비교 → 순자산 증감 → 자산형성/평가손익 → 구성원/자산유형 드릴다운`

### F. 이번 달 돈이 어디로 갔는지 본다
`대시보드 → 총수입 → 소비 / 자산형성 / 금융비용 / 잔여현금 → 고정비·변동비 또는 저축·투자·원금상환 → 실제 거래`

# 23. 데이터 정합성 정책

1. 집계값은 거래 원장을 source of truth로 한다.
2. 카테고리 삭제로 거래 FK가 끊기지 않게 한다.
3. 미래 거래는 `planned` 상태와 실제 거래를 구분한다.
4. 환불은 원거래 수정이 아니라 refund transaction 연결을 권장.
5. 계좌 간 이체는 지출로 집계하지 않는다.
6. 저축성지출은 현금흐름상 지출이지만 순자산 감소로 간주하면 안 된다. 자산계좌 간 이동으로 연결 가능한 구조를 둔다.
7. 대출 원금 상환은 소비지출과 부채 감소를 중복 계산하지 않도록 대시보드의 `생활비 지출`과 `현금 유출`을 분리한다.
8. 카드대금 납부는 카드 사용 거래가 이미 기록돼 있으면 이중 지출 집계 금지.
9. 반복규칙은 예정거래를 생성할 뿐이며 `planned` 상태는 실제 실적/예산소진에 포함하지 않는다.
10. 반복 예정건과 사용자가 직접 입력한 실거래가 매칭되면 한 건만 `posted` 실적으로 집계한다.
11. 보험/적금/대출 상품의 금액 변경은 효력일 이후 회차에만 반영하고 과거 거래를 소급 변경하지 않는다.
12. 상품이 종료/해지/만기/상환완료되면 이후 예정건 생성이 중단되어야 한다.
13. 월말 자산 스냅샷은 당시 확정값을 보존하며 현재 상품값 변경으로 과거 스냅샷을 덮어쓰지 않는다.

이 항목들은 Excel보다 웹에서 반드시 개선해야 하는 부분이다.

# 24. 금융 분석 지표 정의

## 소비성 지출
생활비 성격의 `expense` 합계.

## 저축성 지출
예적금/투자/연금 등 `saving` 합계.

## 현금 유출
expense + saving + 부채원금/이자 등 실제 cash out 기준. 단 계좌 내부 transfer는 제외.

## 저축률
기본: `saving / income`.
설정에서 `(income - expense) / income` 방식도 선택 가능하도록 고려.

## 예산소진율
`budget included expense / budget`.

## 순자산
`assets - liabilities`.

## 전년동기
같은 월/일 경계의 전년도 기간.

## 재무 집계 QA / 계산 정책

모든 대시보드/결산 집계는 동일 SQL View/RPC 또는 공통 서버 계산모듈을 사용한다. 화면별로 다른 수식을 중복 구현하지 않는다.

필수 검증:
- `현금유출 = 소비 + 저축 + 투자 + 대출원금 + 금융비용 + 기타 실제 현금이동` 관계를 테스트한다.
- 적금/투자/대출원금이 소비성지출에 포함되지 않아야 한다.
- 대출 원금과 이자가 분리 집계되어야 한다.
- 자산형성액 = saving + investment + debt_principal posted 합계와 일치해야 한다.
- 순자산 = 총자산 - 총부채와 항상 일치해야 한다.
- planned 거래는 실적 KPI에 포함하지 않는다.
- 평가손익은 자산형성액에 포함하지 않는다.
- 계좌간 transfer는 총소비/총수입/자산형성에 영향을 주지 않는다.

## 고정비/변동비 QA

- expense 거래는 fixed/variable 중 하나를 가져야 한다.
- income/saving/transfer/asset_adjustment에는 비용성격을 강제하지 않는다.
- 카테고리 기본값이 신규 거래에 정확히 복사되는지 확인한다.
- 과거 거래는 카테고리 기본값 변경만으로 자동 변경되지 않아야 한다.
- 반복규칙의 비용성격이 planned 거래에 승계되는지 확인한다.
- fixed + variable 소비 합계가 해당 범위의 전체 소비성지출과 일치해야 한다.
- 대출 원금/저축을 고정비로 잘못 집계하지 않는지 확인한다.

# 28. Excel에서 확인된 주의사항

1. `메인`의 일부 월 집계 수식에서 `#REF!` 참조가 확인됨. 웹 구현 시 해당 깨진 참조를 복제하지 말고 transaction source 기반으로 재산출한다.

4. 수입 금액 컬럼에 텍스트가 들어간 사례가 있어 import validator가 필요하다.
5. Excel의 자산 증감률 계산식과 일반적인 전월 대비 증감률 정의가 다를 수 있으므로 웹 정책을 명시적으로 통일한다.

# 31. MVP 완료 정의 (Definition of Done)

MVP는 화면이 예쁘게 보이는 상태가 아니라 아래가 모두 충족될 때 완료다.

1. 모바일에서 일반 지출 1건을 10초 내 저장할 수 있다.
2. PC `월간관리`에서 해당 월의 직접입력·모바일입력·자동생성 예정건을 한 화면에서 관리할 수 있다.
3. 수입/지출/저축/예산 계산이 기존 Excel의 의미와 일치한다.
4. 보험/적금/대출 등 반복항목이 원천 상품 등록 후 매월 자동 planned 생성되고, 해지/만기/상환완료 후 중단된다.
5. 반복 예정건과 직접 입력 실거래가 이중 집계되지 않는다.
6. 예산·결산과 월말점검이 월간관리 안에서 연결된다.
7. 대시보드에서 년→월→일→거래 및 대분류→소분류→거래 드릴다운이 된다.
8. 전월·전년동월·전년동기 비교가 된다.
9. 자산/부채/순자산 추이와 가족 구성원별 현황을 볼 수 있다.
10. 예금/적금/대출 계산이 Excel 검증값과 일치한다.
11. 인증되지 않은 사용자는 어떠한 개인 금융 데이터도 조회할 수 없다.
12. 사용자 데이터는 RLS로 격리된다.
13. TOTP MFA를 적용한다.
14. Git/Vercel에 비밀키나 Excel 원본이 노출되지 않는다.
15. 핵심 계산, 반복항목 idempotency, RLS에 자동 테스트가 존재한다.

# 33. 최종 제품 판단 기준

이 웹은 “Excel을 예쁘게 웹으로 옮긴 것”이 아니라 다음 상태가 되어야 한다.

- **입력은 모바일이 Excel보다 압도적으로 빠르다.**
- **월말 정리는 PC `월간관리` 하나에서 Excel만큼 빠르거나 더 빠르다.**
- **보험·예적금·대출 등 반복항목은 한 번 등록하면 매월 다시 타이핑하지 않는다.**
- **집계는 행/셀 위치에 의존하지 않아 깨지지 않는다.**
- **숫자를 클릭하면 원인 거래까지 바로 내려갈 수 있다.**
- **가계부 손익과 자산/부채 변화가 한 화면에서 연결된다.**
- **금융 데이터가 인터넷에 올라가더라도 RLS/MFA/secret 관리로 안전하게 보호된다.**

이 기준을 충족하지 못하는 기능은 구현 완료로 보지 않는다.

# 33. v0.5 최종 정합성 규칙

본 문서는 v0.5 기준으로 본문 전체를 수정했다. 구현 시 아래를 최종 규칙으로 사용한다.

- 1차 메뉴는 `대시보드 / 월간관리 / 자산·금융 / 설정` 4개다.
- 별도의 비정기 생활재무 전용 메뉴는 만들지 않는다.
- 정부지원금과 경조사의 **금액**은 반드시 `transactions`가 source of truth다.
- 정부지원금의 신청조건/기간/상태 등은 `transaction_support_details`에 저장한다.
- 경조사의 상대방/관계/행사정보는 `transaction_event_details`에 저장한다.
- 위 두 확장 테이블은 금액 원장을 별도로 만들지 않는다.
- 목표·일정은 `financial_goals`, `financial_tasks`에 유지하되 `설정 > 목표·일정`에서 관리하고 대시보드에서 조회한다.
- 보험/예적금/대출/일반 정기비용은 반복규칙으로 월별 `planned` 거래를 생성한다.
- 실제 실적은 `posted` 거래만 집계한다.
- 상품·반복규칙·거래 간 동일 금액의 중복집계를 금지한다.

# 34. v0.6 추가 정합성 규칙

- 정부지원금은 단발성 수입만 지원하지 않는다.
- 전체 수령기간과 지급주기를 입력하면 해당 기간의 `planned income`이 자동 생성되어야 한다.
- 실제 입금 시 해당 planned occurrence를 posted로 전환한다.
- planned 지원금은 실제 수입 집계에 포함하지 않는다.
- 동일 지원금의 planned/posted 이중집계를 금지한다.
- 지원금 자동생성은 별도 엔진이 아니라 공통 `recurring_rules / recurring_occurrences` 엔진을 재사용한다.

# 35. v0.7 추가 정합성 규칙 — 고정비/변동비

- 소비성 지출은 `fixed / variable` 비용성격을 가진다.
- 비용성격은 카테고리와 독립된 분석축이다.
- `고정비 = 반복거래`로 간주하지 않는다. 반복 여부와 비용성격은 별도 속성이다.
- 카테고리는 `default_cost_behavior`를 제공하고 거래 생성 시 스냅샷처럼 복사한다.
- 반복규칙은 `cost_behavior`를 보유하고 자동생성 거래에 승계한다.
- 적금/투자이체/대출원금 등 자산·부채 이동은 고정비/변동비 소비 분석에서 제외한다.
- 대시보드는 고정비/변동비 금액, 비율, 기간별 추이와 카테고리/거래 드릴다운을 지원한다.

# 36. v0.8 최종 재무 분류 규칙

- 현금유출과 비용을 동일시하지 않는다.
- 소비성지출, 저축, 투자, 대출원금상환, 금융비용은 서로 독립된 분류다.
- 대출원금상환은 소비비용이 아니며 자산형성에 포함한다.
- 대출이자/금융수수료는 금융비용이다.
- 고정비/변동비는 금액의 동일성보다 경제적 성격과 조정 가능성으로 판단한다.
- 적금/투자/대출원금상환은 고정비/변동비 소비 분석에서 제외한다.
- 생활수지, 현금잔여액, 자산형성액, 순자산은 각각 별도의 KPI다.
- 자산평가손익은 자산형성액과 분리한다.
- 모든 대시보드/결산 화면은 동일한 공통 집계 로직을 사용한다.
