## 감사 후속 반영 (2026-09-04)

감사 이후 다음 변경을 코드에 반영했다.

- 분석의 월별·일별 현금흐름 집계를 반복 `filter()` 방식에서 단일 `Map` 집계로 변경했다.
- 대시보드 최근 6개월 추이도 동일한 공통 집계 함수를 사용하도록 통합했다.
- 기간 합계 계산을 단일 순회로 통합해 수입·지출·저축성 지출·참고 거래를 한 번에 계산한다.
- 거래 가져오기에서 수입 카테고리와 소분류를 함께 매핑하고, 소분류만 입력된 원본도 상위 카테고리까지 추론하도록 보강했다.
- 일반 거래 가져오기 이력의 source type을 `transactions`로 구분하고, 파일명·전체 행 수·오류 행 수를 이력에 전달하도록 수정했다.
- 분석 화면은 전체 거래 조회 대신 드릴다운에 필요한 경량 요약 컬럼만 조회하도록 전환했다.

연간 분석의 DB 레벨 그룹 집계 전환은 드릴다운 상세 거래를 보존하기 위한 별도 API/RPC 설계가 필요해 아직 미완료다. 현재는 경량 요약 조회로 네트워크·직렬화 비용을 줄였다. 반복 거래 화면 진입 시 DB 쓰기는 화면 응답 이후 인증된 클라이언트 동기화로 분리했다. 주요 route에는 `loading.tsx`가 이미 존재하므로, 이후 작업은 skeleton 누락 보완이 아니라 실제 체감 성능 측정과 nested route의 로딩 일관성 검증으로 진행한다.

## 결론

현재 상태는 `빌드 가능`이지만 `운영 품질 검증 완료`로 보기 어렵다. 기본 CRUD와 주요 집계 함수, RLS 방어선은 상당 부분 갖춰져 있으나, 다음 네 가지가 운영 리스크다.

1. 페이지 조회가 반복 거래 생성·예정 거래 확정 같은 DB 쓰기를 직접 수행한다. 새로고침·동시 접속·재시도에 따라 지연과 경합이 발생할 수 있다.
2. 분석 화면은 연간 거래 상세를 한 번에 가져와 클라이언트에서 반복 집계한다. 데이터가 늘면 첫 화면 응답과 브라우저 계산량이 함께 증가한다.
3. 일반 거래 가져오기 화면에 지출 카테고리만 전달된다. 수입 소분류 가져오기/매핑이 누락될 가능성이 높다. (`src/app/(app)/settings/data/page.tsx`)
4. 최초 통합 테스트에서는 Supabase Auth `429 over_request_rate_limit`가 발생했지만, 후속 전체 테스트에서는 43개 파일·198개 테스트가 모두 통과했다. Auth rate limit은 재발 가능성이 있으므로 CI에는 재시도·격리 전략이 필요하다.

## 실제 화면 증거

브라우저로 운영 주소를 새 세션에서 열었고 로그인 화면까지 확인했다. 현재 브라우저 세션에는 인증 상태가 없어 로그인 후 대시보드·월간관리·분석·자산·설정 화면은 캡처하지 못했다.

![운영 로그인 화면](../output/audit/current-login.png)

확인된 로그인 화면은 제목·보조 문구·입력 필드·주 CTA의 위계가 분명하고, 첫 사용자를 위한 회원가입 진입도 존재한다. 다만 인증 이후 화면의 실제 레이아웃·드로워·테이블·모바일 반응형은 이번 실행에서 검증 대상에서 제외한다.

## 기능 흐름 감사

### 1. 최초 진입·가구 초기화 — 주의

`ensureHouseholdForCurrentUser()`가 인증 사용자 확인, 가구 조회/생성, 기본 카테고리·결제수단 시드를 수행한다. 요청 단위 `cache()`로 같은 요청 내 중복은 줄였지만, 첫 가구 생성은 여전히 여러 DB 작업을 포함한다.

- 좋은 점: 가구 생성 경쟁 시 unique violation을 재조회로 복구한다.
- 위험: 첫 로그인 요청에 시드와 초기화 완료 업데이트가 몰려 첫 화면 지연이 커질 수 있다.
- 개선: 온보딩 완료 단계에서 명시적으로 초기화하고, 화면 렌더링은 초기화 완료 여부만 조회한다. 시드 작업은 idempotent한 단일 RPC 또는 백그라운드 작업으로 묶는다.

### 2. 월간 거래 입력 — 주의

월간 화면이 `materializeRecurringRulesForRange()`와 `promotePastPlannedTransactions()`를 렌더링 중 호출한다. 조회가 곧 쓰기인 구조다.

- 위험: 같은 월을 여러 탭에서 열거나 새로고침할 때 DB 쓰기 경합과 지연이 발생한다.
- 위험: 쓰기 실패가 화면 조회 실패로 전파되어 사용자는 “거래 목록이 안 보임”으로 경험할 수 있다.
- 개선: 예정 거래 생성/과거 거래 확정은 로그인 후 한 번, 명시적 동기화 액션, 또는 스케줄러에서 수행한다. 화면은 읽기 전용이어야 한다.
- 검증 추가: 동일 월 동시 요청 2~5개에서 거래가 정확히 1건만 생성되는 API/DB 통합 테스트.

### 3. 수입·지출 분석 — 주의

분석 페이지는 전년도 12월부터 해당 연도 12월까지 `listTransactions()`로 상세 거래를 읽은 뒤 클라이언트에서 월·유형·카테고리별로 재집계한다.

- 장점: 연도 변경 외에는 브라우저 상태로 탭 전환이 가능하다.
- 위험: 연간 거래 수가 증가하면 최초 응답 payload, RSC 직렬화, 클라이언트 메모리와 계산량이 함께 증가한다.
- 개선: 1차 화면은 월별 집계 RPC/뷰로 반환하고, 상위 항목을 클릭할 때만 하위 소분류·개별 거래를 조회한다.
- 개선: 월/일별 계산을 `filter()` 반복으로 하지 말고 한 번의 `Map` 그룹화로 만든다.

### 4. 자산·금융 — 양호하나 검증 필요

요약 조회는 `Promise.all()`로 병렬화되어 있다. 계좌·예금·적금·대출·보험·기타자산·투자 메뉴가 분리되어 있고, 현재 자산 요약과 스냅샷을 함께 사용한다.

- 확인 필요: 자산 스냅샷을 기록하지 않은 달의 추이 표시가 “0”인지 “데이터 없음”인지 전 화면에서 일관적인지 인증 화면 검증이 필요하다.
- 확인 필요: 투자 거래가 현재 순자산·현금흐름·카드 사용액에 어떤 방식으로 연결되는지 사용자 문구로 명확히 해야 한다.

### 5. 데이터 가져오기·내보내기 — 높음

현재 일반 거래 가져오기 컴포넌트에 전달되는 카테고리는 지출 활성 카테고리로 제한되어 있다.

```tsx
categories={categories.filter((category) => category.transactionType === 'expense' && category.isActive)}
```

이 때문에 수입 소분류가 원본 파일에 있어도 매핑 UI에서 선택할 수 없을 수 있다. 또한 `importTransactionsAction()`은 모든 일반 가져오기를 `sourceType: 'workbook_monthly'`로 기록한다. 실제 CSV/카드사 파일과 월별 원본 엑셀 가져오기가 이력에서 구분되지 않는다.

- 조치: 수입·지출·참고거래에 맞는 전체 활성 카테고리와 소분류를 전달하고 유형별 매핑을 검증한다.
- 조치: import source type을 실제 업로드 종류에 따라 저장한다.
- 조치: 1건·빈 결제수단·수입 소분류·참고거래·환불·중복 재업로드를 각각 자동 테스트한다.

## 데이터·계산 로직 감사

### 확인된 강점

- `flow_class`와 `transaction_type`을 분리해 참고 거래를 수입·지출 집계에서 제외하는 의도가 명확하다.
- 저축성 지출을 총지출에 포함하고 별도 지표로도 보여주는 불변식이 분석 코드에 문서화되어 있다.
- 카드 사용액은 지출과 참고 거래를 합산하고 수입은 제외하는 규칙이 별도로 정의되어 있다.
- 중복 가져오기는 날짜·유형·금액·내용·결제수단 조합으로 재시도 중복을 줄인다.
- RLS 관련 마이그레이션과 교차 가구 테스트가 존재한다.

### 주요 위험

- 중복 키가 내용의 정규화와 결제수단에 의존하므로, 카드사 표기 변경·공백·취소 표기 차이에 대한 의도적 중복 정책이 필요하다.
- `listTransactions()`는 1,000건 페이지를 반복 조회한다. 분석처럼 대량 조회가 필요한 화면에서 상세 컬럼 전체를 사용하는 것은 확장성 한계가 있다.
- `reportMonthOf()`는 `sourceMonth`를 우선한다. 월간관리와 분석의 “거래일 기준” 및 “원본 시트 기준” 목적을 화면별로 명시하지 않으면 같은 거래가 서로 다른 달에 보일 수 있다.
- 원본 엑셀 보존과 사용자 수정 거래의 관계를 데이터 모델에서 명시적으로 구분해야 한다. 원본 보존 필드가 분석 집계에 우발적으로 사용되지 않도록 계약 테스트가 필요하다.

## 프론트엔드·UX 감사

### 코드에서 확인된 구조 문제

- 공통 `PageHeader`, `SectionHeader`, `StatCard`, `MenuCard`가 존재하지만 일부 화면은 여전히 수동 `tds-card p-5`와 직접 작성한 `h2` 구조를 사용한다. 이 상태에서는 제목·설명·액션 간격이 다시 화면별로 갈라질 가능성이 높다.
- 설정의 목표·일정 통합 라우트는 추가됐지만 기존 `/settings/goals`, `/settings/tasks` 라우트도 남아 있다. 사용자가 오래된 링크를 열었을 때 단일 메뉴 원칙과 다른 화면을 보게 될 수 있다.
- 모바일 공통 CTA 규칙이 CSS media query로 전역 적용되므로, 모든 `SectionHeader`의 액션이 모바일에서 100% 너비가 되는지 화면별 회귀 확인이 필요하다.

### 제품 정보 구조 개선 우선순위

1. 대시보드는 “판단과 다음 행동”만 제공하고, 분석은 월/연간 드릴다운에 집중한다.
2. 분석의 상위 행은 수입 소분류 또는 지출 대분류를 보여주고, 클릭 시 소분류/개별 거래를 펼친다.
3. 월간관리는 거래 입력과 예정 거래 처리를 한 흐름으로 유지하되, 분석 리포트는 분석 메뉴로 명확히 분리한다.
4. 설정은 “가구 운영 규칙”과 “데이터 관리”를 구분하고, 가져오기·내보내기·삭제 복구·중복 검토를 같은 관리 영역으로 묶는다.

## 디자인 시스템 감사

### 확인된 강점

- 공통 토큰과 `tds-card`, `SectionHeader`, `StatCard`, `MenuCard`가 있어 통합 기반은 있다.
- 금액에 `tabular-nums`와 `white-space: nowrap`을 적용하려는 규칙이 존재한다.
- 모바일에서 SectionHeader 액션을 전체 너비로 내려보내는 공통 규칙이 추가됐다.

### 남은 문제

- `design-system.css`에 레거시 화면 대응용 선택자와 컴포넌트별 예외가 많이 남아 있어, 같은 카드라도 DOM 마크업에 따라 스타일이 달라질 수 있다.
- 테이블·상태 셀렉트·폼 필드·드로워·토스트가 하나의 컴포넌트 계약으로 완전히 강제되는지 정적 검사가 없다.
- 디자인 토큰 변경 시 모든 화면을 자동으로 캡처·비교하는 회귀 검증이 없다.
- 이번 실행에서는 인증 후 화면을 캡처하지 못했으므로 실제 모바일/웹 픽셀 정렬, 중첩, 줄바꿈, 드로워 침범은 판정하지 않는다.

## 보안·품질 감사

- RLS 마이그레이션과 교차 가구 방어 테스트가 있다는 점은 긍정적이다.
- 그러나 이번 전체 테스트 실행은 `42 passed, 16 failed`였고, 실패 원인은 제품 assertion이 아니라 Supabase Auth `429 over_request_rate_limit`이었다.
- 테스트가 외부 Auth rate limit에 직접 의존하면 배포 전 신뢰도가 떨어진다. 테스트 사용자 재사용, sign-in 호출 수 축소, 테스트 전용 Auth 프로젝트, 또는 서버 검증 토큰 재사용을 검토해야 한다.
- export API는 2차 인증과 감사 로그가 의도되어 있으므로, CSV/JSON 각각에 대해 미인증·미완료 MFA·타 가구 접근 테스트를 별도로 고정한다.
- 사용자 입력은 서버 경계에서 계속 Zod 또는 동일 수준의 명시적 스키마 검증을 유지해야 한다. 클라이언트 `required`만으로 필수 정책을 보장하면 안 된다.
